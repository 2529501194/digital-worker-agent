# 研究数字员工系统 — 整体设计方案

> 版本：v0.1（MVP 设计稿）
> 目标：一个可实际运行的最小版本（MVP），能自主完成"调研 Coding Agent 技术架构并产出 Markdown 研究报告"这类长时研究任务；可中断恢复、可观测、可扩展为多岗位数字员工平台。

---

## 1. 问题定义与核心挑战

一个研究任务（"调研主流 Coding Agent 架构并写报告"）具有以下特征：

| 特征 | 对系统的含义 |
|---|---|
| **长时运行**（几十分钟~数小时） | 不能依赖单一进程/单一 LLM 会话；必须可中断、可断点续跑 |
| **开放式任务** | 不能预先写死执行步骤；必须由 Agent 自主规划、动态调整计划 |
| **依赖外部世界** | 搜索、网页抓取、代码库/文档读取等能力，且外部服务不稳定 |
| **中间成果多** | 笔记、摘录、证据、草稿需要持久化，供后续步骤与恢复后复用 |
| **结果质量不确定** | 需要"自评 + 迭代改进"机制，而不是单次生成即结束 |
| **未来多岗位并发** | 能力分层：平台公共能力 vs 岗位特有能力 |

核心设计原则：

1. **Agent 循环 + 外部持久化状态**：LLM 无状态，所有状态落在外部存储（任务图/事件流/工件库），任何时刻崩溃都能恢复。
2. **事件溯源（Event Sourcing）**：任务执行的每一步（LLM 调用、工具调用、决策）都写成不可变事件，既是恢复依据，也是可观测/可回放的基础。
3. **工件（Artifact）驱动**：中间成果（笔记、证据、大纲、草稿）是一等公民，结构化存储，支持引用与增量更新。
4. **预算与熔断**：时间、步骤数、token、金额四类预算，超限即暂停并产出"当前状态 + 已获成果"，而非失控。
5. **平台/岗位分层**：运行时、工具、观测、调度是平台能力；提示词、技能包、工具白名单、验收标准是岗位配置。

```
└──────────────────────────────────┬──────────────────────────┼──────┘
┌──────────────────────────────────▼──────────────────────────┴──────┐

  岗位层（配置，不是代码）：
  研究数字员工 = 岗位提示词 + 研究技能包 + 工具白名单(search/fetch/artifact)
               + 验收标准(报告 checklist) + 预算策略
  其他岗位(客服/编码/数据…) = 同一 Runtime + 不同的岗位配置
```

**关键边界**：
- **运行时（每个员工实例一份）**：编排器、Agent 循环、上下文管理 —— 与岗位无关。
- **公共能力层（全平台共享）**：搜索、抓取、沙箱、工件库、观测 —— 被所有岗位复用，统一鉴权、限流、审计。
- **岗位配置（数据，不是代码）**：提示词模板、技能包（Skill = 一段可注入的 SOP + 工具子集 + 验收 checklist）、预算策略。新增岗位 = 新增一份配置，不改运行时。

## 3. 模块设计

### 3.1 任务编排器 Orchestrator（数字员工的大脑骨架）

以**状态机 + 计划（Plan）为驱动**，而非写死步骤。宏观阶段：

```
INIT → PLAN → EXECUTE ⇄ VERIFY → WRITE → SELF-CHECK → (ITERATE ≤ N) → DONE
             ↑            │
             └─ 计划修订 ◄─ VERIFY 发现证据不足/方向偏差
```

- **PLAN**：LLM 依据任务描述生成结构化研究计划（子问题列表、每个子问题需要的资料类型、预期产出）。计划本身是一个持久化工件，可被后续步骤修订（"根据过程中获得的新信息调整后续工作"就发生在修订计划这一步）。
- **EXECUTE**：逐个子问题驱动 Agent 循环（3.2）：搜索 → 阅读 → 摘录入工件库 → 更新该子问题的证据与结论。
- **VERIFY**：对照计划检查每个子问题的证据充分性（引用数、来源多样性、是否回答到位），输出 gap 列表；gap 非空 → 修订计划 → 回 EXECUTE。
- **WRITE**：基于工件库中的证据生成报告草稿（大纲 → 分节 → 汇总），所有论断必须挂引用。
- **SELF-CHECK**：按岗位验收 checklist 自检（覆盖度、引用有效性、逻辑连贯），不达标则迭代修订报告（次数受限）。
- 每个阶段转换都写事件，且**阶段粒度即恢复粒度**：崩溃后从最近完成阶段/子问题恢复。

### 3.2 Agent 循环 AgentLoop（微观执行引擎）

经典 ReAct 循环，每个子任务一段：

```
loop:
  1. 组装上下文（系统提示 + 岗位技能包 + 当前子任务 + 相关工件摘要 + 最近轨迹）
  2. LLM 决定下一步动作：调用工具 / 产出工件 / 宣布子任务完成
  3. ToolRouter 执行动作，结果作为 observation 写回事件流
  4. 达到子任务完成条件或步数上限 → 结束该循环
```

- LLM 输出采用**结构化动作协议**（JSON）：`{action: "search|fetch|read_artifact|write_artifact|finish_subtask", args: {...}}`，解析失败自动重试（带纠错提示），连续失败则降级为强制收尾。
- **上下文管理器 ContextMgr**：
  - 滑动窗口 + 分层摘要：旧轨迹滚动压缩为摘要（LLM 生成，存事件流）；
  - 工件摘要常驻：计划、各子问题结论摘要始终可见，原始长文本按需取回（`read_artifact`）；
  - 上下文预算（如 120k tokens）超限触发压缩，压缩本身也是一个可观测事件。

### 3.3 模型网关 ModelGateway（应对模型/外部服务不稳定）

- 多 provider 抽象（OpenAI 兼容接口为主，可挂 Claude/Gemini/本地模型）。
- **重试**：指数退避 + 抖动，区分可重试错误（超时/429/5xx）与不可重试错误。
- **降级链**：主模型（如强推理模型）→ 备模型 → 小模型兜底；不同阶段可用不同模型（PLAN/VERIFY 用强模型，EXECUTE 中机械性步骤用小模型省钱）。
- **熔断**：连续失败 N 次熔断该模型 M 分钟，期间走降级链。
- 所有调用记录（模型、耗时、token、成本、错误码）写入事件流 → 观测中心。

### 3.4 工具系统 ToolRouter + 公共能力

统一工具协议（JSON Schema 描述输入输出），运行时按岗位白名单过滤：

| 工具 | 说明 | 归属 |
|---|---|---|
| `web_search` | 搜索接口（SerpAPI/Brave/自研），返回标题+摘要+URL | 公共 |
| `web_fetch` | 抓取网页并转 Markdown（带缓存、robots 检查、大小上限） | 公共 |
| `read_artifact` / `write_artifact` / `list_artifacts` | 工件库读写（笔记、摘录、证据、大纲、草稿） | 公共 |
| `code_exec` | 沙箱内执行代码（数据处理等），资源限制 | 公共（研究岗可不开） |
| `vector_search` | 对已抓取语料的向量检索（语料大时替代反复全文读取） | 公共（可选） |

- 每个工具调用：参数校验 → 限流（每任务/每分钟配额）→ 执行 → 结果截断（防单次灌爆上下文）→ 写事件。
- 工具失败不直接终止循环：把错误作为 observation 返回给 LLM，由 LLM 决定换关键词/换来源/跳过。

**工件（Artifact）模型**（研究岗核心数据结构）：

```
Artifact {
  id, task_id, type: note|evidence|outline|draft|plan,
  title, content(md/json), refs: [url/其他artifact],
  updated_at, version, status: draft|verified
}
```

### 3.5 可靠性：中断、恢复与长时运行

这是"真实生产环境"的核心要求：

1. **事件溯源 + 检查点**
   - 事件流（append-only）：`task.created / stage.started / llm.called / tool.called / artifact.written / plan.revised / stage.completed / task.paused …`
   - 每完成一个子任务/阶段写 checkpoint（`{stage, subtask_cursor, plan_version, context_snapshot_id}`）。
   - 进程崩溃/重启 → 加载 checkpoint + 重放事件流中该 checkpoint 之后的事件 → 从断点继续。**LLM 无状态，恢复零成本。**
2. **幂等与去重**
   - 工具调用带 `attempt_id`；重放时已完成调用直接取缓存结果，不重复执行外部副作用（如重复抓取）。
   - 工件写采用 version 递增，天然幂等。
3. **看门狗与心跳**
   - 运行中的任务每 T 秒写心跳；调度器检测心跳超时 → 标记 `stuck` → 尝试恢复或告警。
4. **优雅暂停/取消**
   - 每个循环边界检查控制信号（pause/cancel/budget_exhausted）；暂停时落 checkpoint，可后续 resume。
5. **预算控制**：`{max_duration, max_steps, max_tokens, max_cost}`，软限触发"收尾模式"（停止开新子任务，尽快完成报告并标注未完成部分），硬限强制暂停。
6. **外部服务抖动**：搜索/抓取失败自动重试；单来源不可用 → LLM 换来源；全局降级策略（如搜索 API 挂 → 用 Bing 兜底或直接抓已知站点）。

### 3.6 观测中心：让开发者"看懂任务怎么跑出来的"

三层观测：

1. **事件时间线（Event Timeline）**：按任务维度聚合全部事件，人类可读的逐步叙事（"12:01 计划生成 5 个子问题 → 12:03 搜索 'Claude Code architecture' 得 8 条 → 12:05 抓取 A 失败(403)，重试成功 → …"）。这是排障第一入口。
2. **Trace（OpenTelemetry）**：一个任务 = 一个 trace，每次 LLM/工具调用 = span（含 token 数、耗时、成本、模型、错误），可接入 Jaeger/Zipkin。
3. **审计与回放**：
   - LLM 调用保留完整 prompt/response（可配置脱敏级别）→ 可精确复现任何一步；
   - "为什么报告里这句话是错的" → 沿引用链回溯：报告段落 → 工件 → 事件 → 原始抓取内容（抓取原文也缓存）。
   - 失败分析看板：按错误类型聚合（模型 429、抓取 403、计划反复震荡…），驱动策略调优。

### 3.7 多岗位扩展：平台能力 vs 岗位能力

| 能力 | 归属 | 理由 |
|---|---|---|
| Agent 运行时（编排/循环/恢复/上下文管理） | **平台** | 所有岗位同构，换岗位不该重写运行时 |
| 模型网关、工具框架、工件库、观测、调度、预算/计费 | **平台** | 共享基础设施，统一限流/审计/成本核算 |
| 提示词、技能包（SOP+验收标准）、工具白名单、预算策略、岗位 KPI | **岗位配置** | 岗位差异全部收敛在这里；新增岗位=加配置+加测试 |
| 岗位专属工具（如编码岗的 git 工具、客服岗的工单 API） | **岗位插件** | 实现平台统一 Tool 接口，按岗位挂载 |

调度器支持 N 个数字员工实例并发（每个任务独立 worker/进程 + 隔离的工作目录与工件命名空间），资源通过队列+配额管理。

## 4. 技术选型（MVP）

| 项 | 选型 | 说明 |
|---|---|---|
| 语言/框架 | Python 3.11 + FastAPI | API 服务 + 任务 worker 同仓 |
| Agent 实现 | **自研轻量循环**（不引 LangChain 等重框架） | 核心循环 <500 行，恢复/事件/预算逻辑完全可控；框架只当可选适配器 |
| LLM | OpenAI 兼容接口（主）+ 多 provider 可配 | 网关层统一，可挂任意兼容端点 |
| 存储（MVP） | SQLite（事件流/任务/工件/检查点单文件库） | 生产切 PostgreSQL，接口不变 |
| 工件/抓取缓存 | 本地文件系统（`artifacts/{task_id}/...`） | 生产切对象存储（S3 兼容） |
| 向量检索 | MVP 不做；预留接口，需要时上 SQLite-vec/FAISS | 语料不大时 `read_artifact` + 全文检索足够 |
| 搜索 | SerpAPI/Brave API（key 可配），失败降级 Bing HTML | 一个 Provider 接口 |
| 抓取 | httpx + readability-lxml → Markdown，LRU 缓存 | |
| 观测 | 结构化 JSONL 事件日志 + OpenTelemetry SDK（span 导出可选） | 默认零外部依赖即可排障 |
| 并发（生产） | Celery/独立 worker 进程 + 队列 | MVP 用单进程 asyncio worker |
| 测试 | pytest：循环单测（mock LLM）、崩溃恢复集成测试（kill 进程后 resume）、端到端小任务 | |

## 5. 一次研究的典型执行过程（示例叙事）

任务："调研当前主流 Coding Agent 的技术架构，比较任务规划/工具使用/上下文管理差异，输出 Markdown 报告。"

1. **PLAN**：LLM 产出计划工件 P1：识别 4~6 个主流 Agent（Claude Code、Codex、Cursor、Devin、Aider、OpenHands…）→ 子问题：各自架构、规划机制、工具系统、上下文管理、官方文档/论文来源。
2. **EXECUTE**（每个子问题一个 Agent 循环）：
   - `web_search("Claude Code architecture agentic loop")` → 选 3 个来源 → `web_fetch` 转 Markdown → 截断入上下文 → LLM 写 evidence 工件 E-xx（摘录 + 关键论断 + 来源）。
   - 中途发现某 Agent 有技术博客深入讲上下文压缩 → **修订计划 P2**，新增该子问题（体现"根据新信息调整"）。
   - 某站点 403 → 自动重试 → 换来源，全程事件留痕。
3. **VERIFY**：发现"Devin 的工具系统"证据只有 1 条且过时 → 回 EXECUTE 补强。
4. **WRITE**：大纲工件 → 分节草稿 → 汇总报告，论断逐条挂 `refs`。
5. **SELF-CHECK**：对照 checklist（每家覆盖三大比较维度？引用可点击？有无无引用论断？）→ 迭代 1 次修订 → **DONE**，产出 `report.md` + 完整事件时间线。

期间任一步崩溃：重启后从 checkpoint 恢复，已完成的搜索/抓取/摘录不重做。

## 6. 失败模式与对策清单

| 失败 | 检测 | 对策 |
|---|---|---|
| LLM 超时/429/5xx | ModelGateway | 退避重试 → 熔断 → 降级模型 |
| 进程崩溃/机器重启 | 心跳超时 | 事件重放 + checkpoint 恢复 |
| 外部站点不可达/403 | 工具错误 | 重试→换来源→跳过并记录 gap |
| 计划震荡（反复修订） | plan 版本号监控 | 修订次数上限，超限锁定计划 |
| 上下文爆炸 | token 计量 | 滚动摘要压缩 + 工件外置 |
| 结果质量差 | VERIFY/SELF-CHECK 不过 | 迭代上限内修订；超限则交付 + 明确标注未完成项 |
| 预算耗尽 | 预算管理器 | 软限收尾 / 硬限暂停，均落检查点 |
| 死循环刷同一动作 | 动作去重窗口 | 相同 action+args 连续 K 次 → 注入提示强制换路 |

## 7. 交付与里程碑

- **M1（第 1 周）**：骨架 —— 事件流、checkpoint、Agent 循环、mock LLM 跑通 PLAN→EXECUTE→WRITE；单测。
- **M2（第 2 周）**：真接入 —— ModelGateway（真模型 + 降级）、web_search/web_fetch、工件库；跑通一个缩小版研究任务（3 个对象）。
- **M3（第 3 周）**：生产化 —— 预算/熔断/心跳/恢复集成测试（kill -9 后 resume）、观测时间线 CLI、完整研究任务端到端 + 崩溃注入测试。
- **M4**：平台化 —— 岗位配置加载器、多任务并发 worker、PostgreSQL/对象存储切换、OTel 导出。

**验收标准（MVP）**：
1. 提交研究任务后无需人工干预，产出带引用的 Markdown 报告；
2. 运行中 `kill -9` 进程，重启后自动从断点继续且无重复外部调用；
3. 任意任务可通过事件时间线回答"这一步为什么这么做、结果从哪来"；
4. 搜索 API 被 mock 为全挂时，任务降级但能给出明确失败报告而非死循环。
