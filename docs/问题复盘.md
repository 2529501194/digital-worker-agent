## 一、用户反馈的问题

### 问题 1：报告生成后，点"研究报告"标签页没有反应

- **现象**：任务跑完、报告已生成，前端点"研究报告"标签无任何显示。
- **根因**：迷你 Markdown 渲染器 `md()` 中，`closeList` / `closeQuote` 两个闭包定义在 for 循环**内部**（块级作用域），循环结束后的收尾调用 `closeList()` 抛出 `ReferenceError` → `loadReport()` 的 promise 被静默吞掉 → 报告区域**永远空白**。
- **定位方法**：用 Node + 极简 DOM 桩执行页面内联脚本，复现并捕获 `unhandledRejection` 指认。
- **修复**：两个闭包提升到循环外；顺带增加"任务运行中停留在报告页时，占位提示随轮询自动刷新"。
- **提交**：`2c155ee`

### 问题 2：报告"对比分析"章节写死"任务规划 / 工具使用 / 上下文管理"

- **现象**：提示词换成"当前手机市场分析"，报告的对比维度仍是 Coding Agent 专属的三个维度，与研究主题无关。
- **根因**：`WRITE_PROMPT` 里把三个维度硬编码进报告模板；`PLAN_PROMPT` 的示例也是 Agent 导向的。
- **修复**（让维度跟着主题走）：
  1. PLAN 阶段 JSON 新增 `compare_dimensions`（2–4 个，**要求由研究主题本身推导**），与子任务一起写入 `plan.created` 事件和计划工件；
  2. `WRITE_PROMPT` 改为 `{dims}` 占位动态注入；计划缺失维度时兜底"自行选择最贴合主题的维度"；
  3. `PLAN_PROMPT` 去掉 Agent 硬编码示例，改为通用要求（主题相关的具体产品/品牌/事件）。
- **验证**：真实 GLM + You.com 搜索重跑"当前手机市场分析" → 维度 `[市场份额, 价格带, 目标人群, 核心卖点]`，报告章节随之正确。
- **提交**：`2c155ee`（含 2 项维度回归测试）

### 问题 3：已完成的任务在任务列表显示 "done 0/3"

- **现象**：任务 t-7e4ed864 实际 3 个子任务全部跑完（`task.completed`），前端进度却显示 `0/3`。
- **根因**：子任务有**三种终态**（`subtask.finished` 正常完成 / `subtask.max_steps` 步数上限收尾 / `subtask.aborted` 解析失败中止），而进度统计只数 `subtask.finished`。真实模型的节奏是"搜索 + 抓取 + 多轮写证据 + 解析重试"，常撞上 8 步上限，以 `max_steps` 收尾 → 不被计入。
- **修复**：
  1. `/api/tasks` 进度计入全部三种终态事件（`subtask.paused` 不计——未完成、可恢复）；
  2. 子任务步数上限 `max_steps` 8 → 12，给真实模型留足"搜 + 抓 + 写证据 + finish"的余步。
- **验证**：新增回归测试（max_steps 收尾计入进度）。
- **提交**：`4ada59c`

### 问题 4：切换任务后事件时间线不显示（只有第一个任务能显示，报告页正常）

- **现象**：连续切换多个任务时，只有第一次能正常看到时间线；再选其他任务，时间线空白，报告页却正常。
- **排查历程**（共三轮，前两轮修掉的都是**真实但非根因**的 bug）：

  | 轮次 | 提交 | 诊断与修复 |
  |---|---|---|
  | 第 1 轮 | `4fb26d3` | ① **轮询竞态**：`pollEvents` 为 async，全局 `since` 游标会被上一个任务仍在途的过期响应污染 → 新任务时间线冻结/混入旧事件。修复：`pollGen` 代数守卫，切换任务后在途响应整体丢弃。② **强制切页**：`updateDetailHead` 对任何 done+有报告的任务都无条件切到报告页，时间线页被盖住。修复：仅在"运行中 → 完成"状态过渡时自动切换。 |
  | 第 2 轮 | `5aa9872` | 怀疑浏览器跑的是**缓存的旧版 JS**（服务端此前不发任何缓存头）。修复：`/` 响应加 `Cache-Control: no-store` + 前端开屏打印版本日志（`frontend v2`）+ 补 `do_HEAD`（此前 501）。 |
  | 第 3 轮（根因） | `7f4771b` | 用户贴出的控制台报错 `Cannot read properties of null (reading 'style')` 一击指认：**`#ph` 嵌套在 `#detail-head` 里面**，`updateDetailHead` 执行 `head.innerHTML = ...` 时把 `#ph` **从 DOM 销毁** → 第二次选任务时 `$("#ph")` 取到 null 抛 `TypeError`，`selectTask` 在 `pollEvents()` 之前就中断 → 时间线永不拉取；4 秒轮询也在同一处抛 unhandled rejection。报告页走手动标签点击（`loadReport` 不依赖 `#ph`），所以不受影响。 |

- **为什么前两轮漏掉根因**：早期 DOM 桩"元素永不销毁"（`querySelector` 永远返回桩对象），把这类 bug 完全屏蔽了。
- **修复**：动态标题内容移入新增的 `#detail-meta` 子容器，`updateDetailHead` 只替换子容器；新增**带销毁语义**的 DOM 回归测试 `tests/frontend_dom_test.js`（`innerHTML` 赋值会真实移除嵌套 id，`querySelector` 返回 null，与浏览器一致）——旧版代码跑该测试会精确复现用户控制台的报错，新版 6/6 通过。
- **提交**：`4fb26d3` + `5aa9872` + `7f4771b`

### 问题 5：任务跑崩后 Web 前端无法恢复，只能靠 CLI resume

- **现象**：任务在 Web 上跑崩后（如 LLM 故障发生在 PLAN 阶段），前端没有可用的恢复入口，用户只能 `python -m app.cli resume --task-id …`。
- **根因**：恢复能力以“存在检查点”为前提。检查点在 `_plan()` **末尾**才落盘——PLAN 阶段崩溃时任务以 `task.failed` 收尾但**没有任何检查点** → `resumable=false`，前端不显示“恢复运行”按钮，API 返回 400；CLI `resume` 同样拒绝。
- **修复**（让失败任务在 Web 上一键可恢复，不依赖检查点是否存在）：
  1. `resume_task` 无检查点时从 `task.created` 事件取回 prompt **整体重跑**（编排器见无检查点自动重新生成计划）；
  2. `/api/tasks` 新增 `has_checkpoint` 字段，`resumable` 改为纯状态判定（paused/failed/interrupted 均可恢复）；
  3. 前端按钮按 `has_checkpoint` 区分文案：“恢复运行”（断点续跑）/“重新运行”（从头执行）+ 提示语，防连点；
  4. `orchestrator._load_plan`/`_plan_dimensions` 改取**最后一次** `plan.created`（重跑会重新生成计划，旧计划作废）；CLI `resume` 同步支持无检查点重跑，与 Web 行为一致。
- **验证**：新增 e2e 测试（PLAN 阶段抛异常模拟崩溃 → task.failed 无检查点 → POST resume 202 → 重跑至 done、报告产出）；DOM 回归新增 failed（无检查点）/interrupted（有检查点）按钮文案与点击场景，12/12 通过。
- **提交**：`fd001c2`

### 问题 6：时间线复盘 t-eb3dbd0f（GLM-5.3 真实运行）：四个瓶颈同时贴线

对一次真实任务（GLM-5.3 + LangSearch，3 子任务，38 次 LLM 调用，362s）做逐事件时间线分析，发现四个互相叠加的问题——**没有任何单点报错，但整体质量与成功率被压到贴线状态**：

| # | 现象（时间线证据） | 根因 | 修复 |
|---|---|---|---|
| 6.1 | 3 个子任务全部以 `subtask.max_steps` 收尾，报告停在骨架 | `max_steps=12` 硬编码于 `AgentLoop`，正常研究模式（多源搜索+抓取+证据整理）根本跑不完 | 参数化：`AppConfig.agent_max_steps`（env `RE_EMP_AGENT_MAX_STEPS`，默认 20、下限 1），CLI/Web 统一注入 |
| 6.2 | 3 次 `read_artifact` 空 id 调用全部报错，浪费 5/36 个执行步（14%） | SYSTEM_PROMPT 只列动作名不给参数表，模型盲猜参数名；且空 id 报错为误导性的 “artifact 不存在: ”（尾部空格=空 id） | SYSTEM_PROMPT 补全工具参数表 + 「不要原样重试」规则；`read_artifact` 支持 `id/artifact_id/path` 别名，空 id 明确报「缺少 id 参数」，未知 id 列出可用工件 id（一步自纠） |
| 6.3 | WRITE 阶段每篇证据只注入 400 字符，报告质量卡在摘要级 | `build_context(..., content_chars=400)` 硬编码于 `_write` | 参数化：`AppConfig.write_evidence_chars`（env `RE_EMP_WRITE_EVIDENCE_CHARS`，默认 4000、下限 200） |
| 6.4 | WRITE 单次 LLM 调用 156s+重试=1，贴 180s 读超时线；长报告随时可能撞超时 | 读超时全局单一窗口（默认 180s），WRITE 阶段生成量远大于 EXECUTE 单步 | WRITE 专用窗口 = 基础 180s × 1.5：`AppConfig.llm_write_timeout`（env `RE_EMP_LLM_WRITE_TIMEOUT`，默认 270）；`Provider/Gateway` 支持 `timeout=` 覆盖且重试翻倍逻辑跟随；旧式两参 LLM 精确回退（只匹配 unexpected-kwarg TypeError） |

- **验证**：+15 项回归（`test_tools` 4、`test_config` 3、`test_orchestrator` 4、`test_llm_gateway` 3、`test_agent_loop` 1）：空 id/别名/工件列举、env 默认/覆盖/下限、max_steps 透传、WRITE 截断字符数、timeout 透传至 provider 与旧式两参兼容、SYSTEM_PROMPT 参数表完整性。
- **提交**：`2778f24`
- **方法论**：四个问题全部来自**事件时间线逐条核对**（步数分布、工具参数、上下文长度、延迟直方图），不靠猜——事件流是性能/质量问题的第一现场（经验 3 的延伸）。

**后续（t-a58c3f76 重跑复盘，`87c5578`）**：同一 prompt 用新代码重跑，报告质量反而更差（2.6k vs 7.3k 字符）。逐事件核对发现两个新问题：

1. **顶层丢参**：模型把 `query` 写在 JSON 顶层（`{"action":"web_search","query":"..."}`）而非 `args` 内，`parse_action` 只读 `obj["args"]` 静默丢弃 → 41/47 次 web_search 失败「缺少 query」；模型不知道自己的参数被丢，反复重试同一结构（子任务 1 二十步全部烧空）。修复：`parse_action` 顶层参数容忍（已知参数键合并进 args）+ 缺参报错给出正确调用示例 + `q/keyword`、`link/href` 参数别名。
2. **零证据塌方**：全任务 0 次 `write_artifact` → WRITE 阶段无证据工件，报告全靠模型自身知识。修复：max_steps 收尾时若全程零证据 → summary/gaps 明示；WRITE 零证据时注入降级边界（报告注明缺乏一手证据、参考文献仅限任务内实际抓取过的 URL、禁凭记忆编造）。

另加两道护栏：`REPEAT_FAIL`（同一失败调用第 2 次出现即强提示换路/落证据）、`llm.called` 事件带 `raw_head`（原文前 300 字符——本次“模型到底输出了什么”在事件流里不可见，正是这次复盘最痛的诊断缺口，从此可见）。

**后续（t-59d18668 重跑复盘，`6cc2523`）**：再跑一次，搜索/抓取全部正常（顶层丢参修复生效），但用户反馈报告“过于分点罗列、每点都带 [E-1] 这类标记，质量反而不如上上版”。逐事件 + 工件 + 提示词核对，根因是上一轮修复引入的**新失衡**：

1. **[E-x] 内部编号泄漏进正文**：`WRITE_PROMPT` 要求“引用证据编号与 URL”，writer 字面执行，把内部工件 ID 写进正文；而参考文献列表是 1..N 编号，读者无法对应 `[E-1]`。修复：提示词改为“引用用文末参考文献序号，严禁出现 [E-x]”，落盘前 `_strip_internal_ids` 正则兜底清除。
2. **证据变厚 → 转录腔**：`write_evidence_chars` 400→4000 后，分点式证据全文灌入，writer 从“改写综合”退化为“1:1 逐条转录”（连 E-1/E-2 重复都原样带进报告）。上上版 400 字截断反而逼出了叙述性扩写。修复：提示词明令“连贯论述、多证据合并去重、不要逐条转录”，同时保留“可结合模型知识补充”的扩写空间。
3. **子任务结论从未进 writer 上下文**：两版任务 3 个子任务全部 max_steps 收尾，而 `_write` 只灌 plan 标题 + 证据——writer 从未拿到任何子任务结论（结构性缺口，被“更厚证据”遮住）。修复：`_subtask_conclusions` 从事件流重建各子任务 summary/gaps 注入 WRITE 上下文（崩溃恢复后仍在）；`subtask.max_steps` 事件持久化 summary/gaps。
4. **max_steps 硬撞顶无收口**：模型一直 fetch 到 20 步用尽，从不调 `finish_subtask`。修复：剩最后 2 步注入 `SOFT_LANDING` 提示（先 `write_artifact` 落证据再 `finish_subtask`，不开新搜索），把“撞顶截断”转成“模型主动收口”。

**方法论补充（经验 9 的延伸）**：参数调优是双刃剑——`write_evidence_chars` 400→4000 修好了“材料不够”，却引入了“转录腔”；质量类参数调完后**必须用同一 prompt 重跑对比报告**，而不是只看事件指标。

## 三、经验沉淀

1. **前端 bug 要用"真语义"复现**：DOM 桩必须模拟元素销毁（`innerHTML` 替换后子元素消失、`querySelector` 返回 null）。宽容的桩会整类漏掉 bug（问题 4 三轮排查的教训）。
2. **诊断顺序：先让用户贴控制台报错**。问题 4 前两轮都是推断（竞态、缓存），用户贴出 `Cannot read properties of null` 后一轮定位根因——报错里的行号与源码逐行核对是最快的路。
3. **事件溯源让一切可定位**：进度异常（问题 3）、状态异常（问题 4）最终都靠 `timeline` 事件流逐事件核对解决。事件流是排障的第一现场。
4. **统计进度要枚举全部终态**：`finished / max_steps / aborted` 都算"已处理"，`paused` 不算（可恢复）。只数一种终态必然在真实模型下出偏差。
5. **提示词/模板不写死 demo 领域概念**：报告结构（对比维度）必须由研究主题在 PLAN 阶段推导，WRITE 阶段注入——模板只留占位符（问题 2）。
6. **静态资源要显式缓存策略**：单页内联 JS 升级后，浏览器启发式缓存会让用户永远跑旧版；`no-store` + 开屏版本日志（控制台可见）是最低成本的防呆。
7. **修 bug 时区分"真 bug"与"根因"**：问题 4 的前两轮修掉的竞态和缓存问题都是真实缺陷（值得修），但不是用户症状的根因。修复后症状仍在 = 回到现象重新归因，不要在同一假设上叠加补丁。
8. **工具参数契约必须写进系统提示词**：LLM 不知道你的工具参数名——SYSTEM_PROMPT 只给动作名不给参数表，模型就会盲猜（问题 6.2 三次空 id）。配套要求：**工具错误信息必须可操作**（说清缺什么参数、去哪里看可用值，而不是 "不存在" 这种无法自纠的话）。
9. **运行时参数不设硬编码**：步数上限、截断字符数、阶段级超时这类"拍脑袋数字"，一律收敛到 `AppConfig` + env（带下限保护），并用**真实任务时间线数据**校准默认值（12 步撞顶、400 字符卡质量、156s 贴 180s 线——三个默认值都来自 t-eb3dbd0f 实测）。
